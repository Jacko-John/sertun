# 测试与验证原则

## 目标：最小充分，关键路径不缺

测试数量不是目标，覆盖率也不是目标。以下内容必须有测试，不能用“先这样”跳过：

- 每个新不变量和所有权转移。
- 每条失败路径：取消、超时、EOF、半关闭、部分读写、连接上限、配对过期、认证失败。
- 每个输入边界：帧长度、版本、截断、配置未知字段、代理响应上限。
- 每个热路径改动：正确性测试加 `-benchmem` 前后对照。

简单字段赋值、平凡封装、内部调用顺序和与实现同构的细节不加测试。已有测试能表达同一约束时优先扩展，不复制同类用例。

## 怎么写

- 优先用真实回环 socket、临时目录和标准库。简单场景不引入 mock 框架或额外测试依赖。
- 用动态端口、显式同步和有界等待。固定端口、盲目 sleep 和无限等待都不接受。
- 连接、监听器和 goroutine 都要清理，测试失败时也要能结束。不能靠测试进程退出来代替清理。
- 断言用户能看到的行为或重要边界，不绑定私有字段布局和内部调用次数。为了注入故障去碰内部状态时，结论仍要落在外部行为上。
- 只有负载或时序本身是被测对象时，才加压和重复。性能耗时阈值不进普通正确性测试。
- 解析远端输入、帧和配置边界的包要有 fuzz target。本地至少跑 5 秒，种子输入留在测试里。
- `staticcheck` 使用 CI 固定版本：`go run honnef.co/go/tools/cmd/staticcheck@v0.8.2 ./...`。
- 并发、生命周期或连接所有权改动用 `-race -count=5` 起步；出现过竞争或时序问题的路径提高次数。
- 数据面改动用相同工具链和负载跑 `-benchmem`，报告 allocs/op、吞吐和 CPU；涉及缓冲或池化时加空闲 RSS 和每连接增长。
- 单元/回环、容器、真实主机和真实代理是不同证据层，不能互相替代。容器证明 Linux 行为，不证明宿主机性能。

## 按影响选检查（硬门槛）

| 改动 | 必须执行 |
| --- | --- |
| 文档、规则、文档链接 | 链接、引用和事实一致；不重跑 Go 测试 |
| 配置或命令行行为 | 对应包行为测试、示例配置 `-check` |
| 转发、协议、并发、连接所有权 | `gofmt`、`go vet`、`staticcheck`、`go test ./...`、`go test -race ./...`；并发改动加重复运行 |
| 输入解析或协议边界 | 上述检查加 fuzz，至少 5 秒 |
| 数据面或热路径 | 上述检查加 `-benchmem` 前后；0 新增 alloc/op，或写明代价并由用户确认 |
| 平台相关行为或构建方式 | 受影响目标的构建；运行语义补对应系统实际运行，容器和宿主机分开记录 |
| 性能优化 | 正确性验证加相同条件前后基准，保留所有轮次 |
| 发布 | 六目标构建、包内容、SHA-256、版本输出和实际运行检查 |

硬门槛不满足不能合并或标记完成。CI 提供统一基线，但不替代本地证据；文档编辑不要求本地重跑 Go 测试。

## 记录结果

报告要写运行环境、检查内容和结果，没执行的验证也要说清楚。不能把“CI 文件已配置”写成“CI 已通过”，也不能把“交叉构建通过”写成“目标系统运行通过”。

资源开销必须带测量条件。没有约定的预算或测量结果时，不得声称内存、CPU、吞吐或延迟已经达标。

性能优化前后要用相同工具链和负载，尽量交错测量，保留所有轮次。吞吐不同的场景同时看单位有效数据的 CPU 成本；缓冲或池化改动同时看空闲和负载 RSS，并说明每连接资源增长。性能阈值不进普通功能 CI，但性能证据必须进改动报告。

生成的 JSON、Markdown 和原始输出是证据，只能新增文件重新测量，不得改写已有结果。
