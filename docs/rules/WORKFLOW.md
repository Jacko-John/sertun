# 工作流程与文档维护

适用于规划、实现、修复和交付。规则里的硬门槛必须满足；文档维护的详细程度按改动规模决定。

## 开工

1. 读[演进规划](../../ROADMAP.md)，确认当前代码、已有验证和任务范围。
2. 先弄清用户要解决什么问题。目的不清就先讨论；有更直接的路子就把取舍讲出来。
3. 改实现时读[架构说明](../ARCHITECTURE.md)和[代码规范](CODING.md)；做验证时读[测试原则](TESTING.md)。
4. 依赖工具、代理、远端或测试环境时，先确认资源和当前状态。缺信息就问，同时把不依赖它的部分推进。

新增功能或调整架构，先在规划里找到对应阶段或候选项，说清目标、边界和验收条件再动手。范围内的小修复可以直接做，不必为每次修改新建阶段或文档。

## 分清要求、选择和证据

- 用户明确要求或确认的内容可以当需求依据，只记确实确认过的。
- 工程选择可以在已有授权内自己定，选可逆、常规的做法；把必要的取舍说清楚，不要写成用户逐项确认过。
- 工作假设要标出假设和影响。缺的决定会影响范围或用户目标时先问；沉默不等于确认。
- 实现事实和验证证据要分开写：代码存在、构建成功、本地测试、真实链路、目标系统运行不是一回事。

后续阶段和候选功能不自动变成实施承诺，按当前任务和已有授权推进。别从项目规则里推导出用户没要求的审批步骤。

## 演进规划怎么更新

- 阶段进入实施时，更新当前目标和下一增量；缺运行证据就标成待验证。
- 只有阶段约定的验收条件都满足，才能标完成，并链接对应证据。
- 候选项进入计划前，说明实际需求、已有证据、成本和验收方式；新能力仍要符合轻量目标。
- 不写没有依据的发布日期、性能承诺或“用户已确认”。
- 阶段、范围或关键取舍变了，记一条简短更新；普通代码编辑不用逐条进规划历史。

## 数据面改动

数据面改动按这个顺序：

1. 先记录基线：同一工具链、同一负载、至少一轮 benchmark，保留原始输出。
2. 再改代码；正确性测试和 race 先过。
3. 用相同条件复测，报告 allocs/op、吞吐、CPU；涉及缓冲或池化时加空闲 RSS 和每连接增长。
4. 没有基线或没有复测，不得用“应该更快”或“没有影响”结案。

热路径范围见[代码规范](CODING.md)。

## 信息放哪

| 内容 | 位置 |
| --- | --- |
| 为什么做、阶段目标、先后关系、当前状态、下一增量与候选方向 | [ROADMAP.md](../../ROADMAP.md) |
| 当前怎么实现、模块边界、行为契约与关键取舍 | [ARCHITECTURE.md](../ARCHITECTURE.md) |
| 代码、接口、测试和工作流程的长期约束 | `docs/rules/` 下对应文档 |
| 实际执行的命令、环境、结果与未执行项 | [VALIDATION.md](../../VALIDATION.md) |
| 用户构建、配置、运行和排错需要的信息 | [README.md](../../README.md) |
| 后续协作者要自动发现的规则入口与环境命令 | [AGENTS.md](../../AGENTS.md) |

同一条规则只在一个地方维护，其他文档链接过去。实现变了更新架构，阶段变了更新规划，规则变了更新规则；只动这次受影响的内容。

## 完成检查（硬门槛）

标记完成前逐项确认：

1. 按[测试原则](TESTING.md)的检查矩阵执行：`gofmt`、`go vet`、`staticcheck`、测试、race 和必要的重复运行。
2. 新不变量、失败路径和所有权转移有测试；缺陷修复有回归测试。
3. 数据面改动有 benchmem 前后；平台语义有实际运行证据或明确标成未验证。
4. 用户可见行为、README、架构和配置说明已同步；链接和事实一致。
5. 生成的结果、发布包和验证记录没有被改写；证据边界写清。
6. 工作区没有临时脚本、调试输出、下载产物和未跟踪垃圾。
7. 报告写清改了什么、为什么、验证了什么、还有什么没验证。

任何一项不满足，不能标记完成。

## 规则怎么改

规则变更要说明动机、影响范围和验证方式；先改规则，再按新规则执行。硬门槛不能为了单次改动临时放宽；确实要放宽时，先修改规则并写出理由。

## 完成和交付

- 先把授权范围内可 review 的结果做完，再报告改了什么、为什么、验证了什么、还有什么限制。
- 按影响选检查，遵循测试原则；检查通过且没有新证据时，停止重复扩展。
- 更新失效引用和受影响的示例。对外或交接内容保持最简，去掉真实凭据、私人端点、机器专属路径和无关过程信息。
- 当前事实撑不起某个结论时，写明未验证范围，留下能执行的下一步。
