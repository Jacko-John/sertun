# 工作流程与文档维护

适用于项目规划、实现、修复和交付。规则用于减少误解与返工，文档维护应与改动规模相称。

## 开始工作

1. 阅读 [演进规划](../../ROADMAP.md)，核实当前代码、已有验证与任务范围。
2. 明确用户要解决的问题。目的不清时先讨论；存在更直接的实现路径时说明取舍。
3. 修改实现时阅读 [架构说明](../ARCHITECTURE.md) 与 [代码规范](CODING.md)；设计验证时阅读 [测试原则](TESTING.md)。
4. 依赖工具、代理、远端或测试环境时，先核实资源与当前状态。缺少必要信息时询问，同时推进不依赖该信息的工作。

新增功能或架构调整先定位到规划中的阶段或候选项，说明目标、边界和验收条件，再实现。范围内的小修复可以直接推进，不要求为每次修改建立新阶段或新文档。

## 区分要求、选择和证据

- **用户明确要求或确认：** 可以作为需求依据，只记录实际确认的内容。
- **工程选择：** 可以在已有授权范围内自主采用可逆、常规的方案；说明必要取舍，不表述为用户逐项确认。
- **工作假设：** 标注假设与影响。缺少的决定会影响范围或用户目标时先询问；沉默不等于确认。
- **实现事实与验证证据：** 代码存在、构建成功、本地测试、真实链路和目标系统运行分开记录。

后续阶段与候选功能不自动构成实施承诺；按照当前任务和已有授权推进。避免从项目规则推导出用户未要求的额外审批步骤。

## 演进规划的状态

- 阶段进入实施时更新当前目标与下一增量；缺少运行证据时标明待验证。
- 只有该阶段约定范围内的验收条件满足，才标记完成，并链接相应证据。
- 候选项进入计划前说明实际需求、已有证据、成本与验收方式；新增能力应继续符合轻量目标。
- 不填写缺少依据的发布日期、性能承诺或“用户已确认”状态。
- 阶段、范围或关键取舍发生变化时记一条简短更新；普通代码编辑不必逐条进入规划历史。

## 信息归属

| 内容 | 维护位置 |
| --- | --- |
| 为什么做、阶段目标、先后关系、当前状态、下一增量与候选方向 | [ROADMAP.md](../../ROADMAP.md) |
| 当前如何实现、模块边界、行为契约与关键取舍 | [ARCHITECTURE.md](../ARCHITECTURE.md) |
| 代码、测试和工作流程的长期约束 | `docs/rules/` 下对应规则文档 |
| 实际执行的命令、环境、结果与未执行项 | [VALIDATION.md](../../VALIDATION.md) |
| 用户构建、配置、运行和排错需要的信息 | [README.md](../../README.md) |
| 后续协作者需要自动发现的规则入口与环境命令 | [AGENTS.md](../../AGENTS.md) |

同一规则只保留一个主要维护位置，其他文档使用链接。实现变化更新架构，阶段变化更新规划，规则变化更新规则；只维护本次受影响的内容。

## 完成与交付

- 先完成授权范围内可 review 的结果，再报告变化、原因、验证与实际限制。
- 按影响选择检查，遵循测试原则；检查通过且没有新证据时停止重复扩展。
- 更新失效引用和受影响的示例。对外或交接内容保持最简，去除真实凭据、私人端点、机器专属路径和无关过程信息。
- 当前事实不足以支持某项结论时，明确未验证范围，并保留可执行的下一步。
