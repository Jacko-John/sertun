# 代码与架构规范

适用于 Go 源码、依赖和运行行为的修改。当前结构见 [架构说明](../ARCHITECTURE.md)，变更流程见 [工作流程](WORKFLOW.md)。

## 风格与职责

- 使用标准 Go 命名和错误处理，修改后运行 `gofmt`。
- 标识符与代码注释使用英文。注释解释意图、边界或不明显的约束，避免复述代码。
- 函数与包围绕已有职责组织；入口处理命令行，核心模块不自行退出进程。
- 优先直接、可读的实现。有真实复用或替换需求时再提取接口，不提前建立通用传输框架、插件系统或多层抽象。
- 只增加当前用途需要的配置项，默认值与校验保持集中，用户可见行为同步到使用说明。

## 网络与生命周期

- 在调用链中显式传递 `context.Context`。每个连接、goroutine、定时器都应有明确的所有者与结束路径。
- 成功移交连接所有权后，原所有者不再关闭它；所有失败路径仍需回收自己的资源。
- 明确处理部分读写、取消、超时、EOF 和支持的半关闭语义，不假设一次读写就是完整消息。
- 对握手、消息长度、等待请求和活动连接设置边界；避免无界队列和由远端请求无限创建 goroutine。
- 控制消息与业务载荷分开处理。载荷路径避免重复解析、序列化、复制和不必要的持续分配。
- HTTP CONNECT 需保留响应后已缓冲的隧道字节；代理路径故障不自动切换到直接连接。

## 错误与可观测性

- 错误提供足以定位操作的上下文，需要保留原因时使用 `%w`。
- 在合适的层记录错误，避免每层重复记录同一失败。
- 不记录 token、代理凭据和业务载荷；解析错误也要避免带出完整凭据 URL。
- 日志与配置说明用于解释用户可以采取的行动，避免在使用流程中暴露无用的内部细节。

## 依赖、优化与平台

- 优先使用标准库。引入依赖前说明现有方案不足、具体收益和维护成本。
- 优化必须对应测量结果或明确成本，尽量保留系统提供的高效 I/O 路径。
- 重用缓冲、预建连接等优化需同时评估空闲占用、并发增长和退出回收，不能只报告吞吐提升。
- 不把 Linux 特定能力放入通用路径；平台差异集中封装，并明确构建与运行证据。
- 优先保持纯 Go 构建；引入 CGO 或新的平台前提时，在规划和构建说明中说明理由与影响。

## 修改边界

- 行为改变同时考虑配置、协议、关闭语义和资源上限是否受影响。
- 不在一次修复中顺带进行无关重构或扩展功能。
- 测试选择遵循 [测试原则](TESTING.md)，不因代码行数增加而机械增加测试。
