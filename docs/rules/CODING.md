# 代码与架构规范

适用于 Go 源码、依赖、接口和运行行为。当前结构见[架构说明](../ARCHITECTURE.md)，改动流程见[工作流程](WORKFLOW.md)，完整检查矩阵见[测试原则](TESTING.md)。

## 硬门槛

以下任一项不满足，改动不能标记完成：

- `gofmt -l .` 无输出。
- `go vet ./...` 和固定版本的 `staticcheck ./...` 通过。
- `go test ./...`、`go test -race ./...` 通过；并发或生命周期改动按测试原则重复运行。
- 数据面改动附相同工具链的 `-benchmem` 前后对照；没有测量不得声称没有性能回归。
- 平台相关行为有对应系统的实际运行证据，或者明确标成未验证。
- 用户可见行为变了，配置说明、README 和架构文档同步更新。
- 工作区没有临时脚本、调试输出、下载产物或未说明的生成文件。

## 像 C 一样写 Go

- 先想数据：谁分配、多大、谁释放、在哪个 goroutine 上访问。控制流要能从上往下直接读出来。
- 明确写出分配、拷贝、缓冲和系统调用。不要让接口、闭包、反射或运行时机制把成本藏起来。
- `defer` 只用于函数级清理，不放进每字节或每块循环。数据面需要立即释放时直接关闭或归还。
- 禁止反射、`unsafe`、带副作用的 `init()` 和可变全局状态。进程级、并发安全、有测量依据的缓冲池，只读的包级数据，以及不可变哨兵错误和链接参数注入的版本变量除外。`any` 只允许出现在序列化或标准库 API 边界，并写清原因。
- 不为省几行写泛型、函数式选项、builder、fluent API 或依赖注入。参数多到影响阅读时用小结构体，不引入框架。
- 接口只放在真实边界：`io.Reader` / `io.Writer`、可替换的实现、标准库约定。测试用真实 socket，不为 mock 抽接口。
- map 和动态切片不放进每字节路径；大小已知时预分配；固定大小的小缓冲用数组。
- 错误立即检查，库代码不得 panic，禁止用 `panic`/`recover` 做控制流。启动参数错误由入口处理，核心模块不退出进程。
- goroutine 和 channel 都是显式资源：谁启动、谁等待、什么条件结束。库函数不得隐藏后台 goroutine。
- 优先简单循环、`switch` 和小状态机，不写链式组合和层层闭包。

## 热路径

数据面包括：

- `internal/streamcopy` 的 `Copy`、`copyBuffered`、`copyTCP` 和 `bufferedConn` 读写路径。
- `internal/relay.Bridge` 的双向复制。
- 服务端和客户端的每连接控制循环：`handleTunnel`、`controlSession`、`runSession`。

规则：

- 每字节或每块路径禁止新增分配、接口包装、反射、格式化、日志和锁竞争。
- 热循环不得为了可读性拆成每块调用的函数。结构拆分只能放在每连接、每会话或每请求层级。
- 必须保留 `ReaderFrom`、`WriterTo`、splice 等系统快路径。新增包装时必须同时提供拆包或回退路径和契约测试。
- 缓冲大小、池化和预建连接要同时报告吞吐、CPU、空闲 RSS、并发增长和退出回收。
- 热路径改动必须写清 syscall、分配和拷贝次数的变化。只报吞吐百分比不够。

## 代码风格

- `gofmt` 是底线，不讨论格式偏好。导入按标准库、第三方分组。
- 标识符和注释用英文。导出的类型、函数和方法必须有 doc comment，说明用途、所有权、错误行为和并发约束；导出字段只在语义不明显时加注释。
- 每个文件开头写职责；包注释只放在主文件。注释解释意图、边界和不明显的约束，不逐句复述代码，不叙述修改历史。
- 函数按职责分段，段间空行；长函数在段首说明用途。不为长度强行拆函数，也不把多个意图塞进一个函数。
- 一个语句做一件事。条件复杂时先命名；不用一行里的多级调用、嵌套闭包或连续类型断言压控制流。
- 错误显式处理。产品路径忽略返回值必须有注释说明为什么安全；关闭、清理和向 stderr 输出诊断可以 best-effort，benchmark 的诊断采样也不能影响结果。禁止用 `_ = err` 掩盖失败。
- 禁止注释掉的代码、死分支、未使用的参数/字段/导入、调试输出，以及没有具体计划的 TODO。
- 魔法数字要有名字和单位；常量集中在使用处附近，不建无意义的常量墙。
- 平台差异用 build tag 或独立文件封装，不把 Linux 特有逻辑放进通用路径。

## 接口设计

- 默认不导出。只有另一个包真的需要时才导出。公共 API 是最小承诺，不是功能菜单。
- 一个操作只有一个入口。不要同时提供 `x`、`xOrError`、`xSafe` 这类只在文档里区分行为的变体。
- 消费方定义接口，生产方返回具体类型；接口保持 1 到 3 个方法。只有真实替换需求时才抽接口。
- 嵌入只用于明确的接口转发，并在类型注释里写清被提升的方法；不用嵌入来省字段或模拟继承。
- 函数签名写清所有权和生命周期：谁关闭连接、返回后谁拥有、取消由谁触发、出错后连接是否可用。
- 错误是接口的一部分。调用方需要区分时才用哨兵错误；否则用 `%w` 保留原因并补上下文。禁止用错误字符串做控制流。
- 配置和选项只加当前调用方需要的字段；默认值和校验集中在一处。不为想象中的调用方预留开关。
- 协议或公开行为变化必须说明版本处理、不兼容行为和迁移方式；不能静默改变语义。
- 不为单一调用方建通用框架、插件系统或多层抽象。抽象必须有第二个真实调用方或测量依据。

## 网络与生命周期

- `context.Context` 显式传递，放在函数第一个参数，不存进结构体，不用它传业务数据。每个连接、goroutine 和定时器都要有所有者、上限和结束路径。
- 连接所有权移交后原所有者不再关闭；失败路径谁创建谁回收。
- 部分读写、取消、超时、EOF 和半关闭必须显式处理，不得假设一次读写就是完整消息。
- 握手、消息长度、等待请求和活动连接都要有上限。禁止无界队列和由远端输入无限创建 goroutine。
- 控制消息和业务载荷分开处理。业务路径禁止重复解析、序列化、复制和持续分配。
- HTTP CONNECT 必须保留响应后的缓冲字节。代理失败不得自动回退直连。

## 错误与日志

- 错误带足够定位操作的上下文；保留原因时用 `%w`。
- 在合适的层记录错误，禁止每层重复记录同一个失败。
- 不记录 token、代理凭据和业务载荷。解析错误也不能带出完整的凭据 URL。
- 日志和配置说明告诉用户能做什么，不在使用流程里堆内部细节。

## 依赖、平台与资源

- 优先标准库。新增依赖必须说明现有方案差在哪、收益、维护成本和二进制/内存代价。
- 优化必须有测量结果或明确成本依据，保留系统已有的高效 I/O 路径。
- 缓冲复用、预建连接和池化要同时评估空闲占用、并发增长和退出回收，不能只报吞吐提升。
- 默认保持纯 Go 构建。引入 CGO 或新的平台前提时，在规划和构建说明里写清理由和影响。
- 发布构建记录各目标二进制大小；空闲 RSS 引用已有 benchmark 报告，不为发布重复造数。没有说明的持续增长不接受。

## 改动边界

- 行为变了，要一起检查配置、协议、关闭语义和资源上限。
- 数据面改动不得夹带无关重构；风格整理不得改变行为。
- 新公开 API、配置项或协议字段必须同时有测试、文档和兼容性说明。
- 测试按[测试原则](TESTING.md)选，不为覆盖率加机械测试。
