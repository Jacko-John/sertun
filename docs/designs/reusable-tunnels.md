# 业务通道顺序复用

状态：后续实现项，尚未实现。当前发布版本仍在每次业务结束后关闭业务回连。

## 目标与范围

在保留 Linux splice 和裸数据通道的前提下，减少连续短连接的重复拨号成本。每条通道同一时间承载一个业务；正常结束并确认后立即回池，连续空闲 60 秒才关闭。空闲超时可配置，空闲池与活动通道共同受每客户端资源上限约束。

复用对象仅为 sertun 客户端与服务端之间的业务通道。访问者和本地服务的 TCP 连接各自正常结束，不复用 SSH、HTTP 等应用会话。不增加并发多路复用，不预先填充固定数量的连接。

## 通道与业务边界

控制连接继续承担身份与会话管理，并新增通道分配、方向结束和回收确认。每条通道有独立标识，每次分配有新的业务标识；所有控制消息同时绑定当前控制会话，拒绝过期消息。

业务通道只传载荷，不插入持续数据帧头或结束标记。传输期间沿用原生 TCP 复制。业务源端读到正常 EOF 后，根据复制函数成功写入的字节数，经控制连接通知本方向的最终长度，不对可复用通道发送 FIN。

控制消息与载荷没有跨连接到达顺序保证。接收端必须按本方向最终字节数完成交付，才能把 EOF 传给真正的业务端；不能将收到结束通知视为数据已经到齐。最终计数不一致、方向提前物理 EOF 或数据交付失败时，销毁整条通道。

两个方向独立结束。一个方向完成后，对真正的业务目标执行 `CloseWrite()`，另一方向继续传输；仅当双方确认两个方向均已完成，旧复制任务全部退出，才允许复用。

## 保留 Linux splice 的收尾方案

持续传输使用原生 TCP 的 `ReadFrom` 路径。结束通知到达后，需要协调接收方向停止等待物理 EOF：

1. 由本方向唯一所有者设置源通道的读 deadline，唤醒读等待。
2. 等待原复制任务退出，取得成功交付的累计字节数，再清除此次读 deadline。
3. 若尚有未交付数据，以原生 TCP 为底层、通过 `io.LimitedReader` 精确复制剩余字节，校验完整交付。
4. 完成业务端半关闭，发送本方向的交付确认。

Go 的 Linux 实现会识别 `io.LimitedReader` 并限制 splice 的剩余长度，见 [标准库源码](https://go.dev/src/net/splice_linux.go)。源读 deadline 也不能立即打断阻塞中的目标写入；必须等待已取入内核 pipe 的数据完成写出，或在收尾超时后销毁通道。真实复制错误不能当作可恢复的协议唤醒继续传输。

该协调方式需要 Linux 实际验证，包括部分进度、目标背压和 deadline 竞争；目前只有标准库路径的实现依据。其他系统沿用用户态复制，遵守相同的业务边界。

## 分配与空闲回收

服务端统一管理通道的分配和空闲过期，避免两端独立抢占。建议状态为：

`新建 → 分配中 → 转发中 → 收尾中 → 空闲 → 分配中`，任意状态均可转为关闭。

- 新访问优先取空闲通道，没有可用通道时按需新建。
- 收尾确认前，不允许开始下一业务，也不允许新旧读取任务重叠。
- 入池即启动 60 秒空闲计时；再次分配取消旧计时，下次入池重新计时。
- 过期回收与新分配必须由同一个状态转换决定胜者。池满时关闭多余空闲通道。
- 空闲时释放业务缓冲和复制任务，仅保留连接与必要状态。
- 控制会话失效时关闭该会话全部活动和空闲通道。
- 第一版仅复用正常收尾的通道。异常、计数不符、对端失效和收尾超时均销毁通道；业务数据发送后不自动重放请求。

## 兼容性与验收

新增控制消息改变协议能力，实施前明确版本协商和不兼容拒绝行为，不把旧实现的物理 EOF 当成可复用结束。

按 MVP 加合理增量验证：

- 同一通道连续承载两个不同内容的业务，覆盖单向先结束、反向尾部数据及控制消息先于载荷到达，确保不串流、不截断。
- 覆盖收尾时的目标背压、取消或失败，以及过期回收与新分配竞争，确认连接、任务和资源上限可回收。
- 在 Linux 实际核实持续传输与限长收尾仍经过 splice；macOS / Windows 验证同等关闭语义。
- 以相同工具链和链路对照短连接延迟、长流 CPU / 吞吐及空闲池资源增长。60 秒为空闲保留初值，不代表已验证的最佳参数。

实现顺序：先完成业务边界与收尾，再接入空闲池，最后验证资源与性能。不将这项设计作为 HY2 多连接退化的既定修复。
