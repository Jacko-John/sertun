# 业务通道顺序复用

状态：后续实现项，还没写。当前版本每次业务结束都会关掉业务回连。

## 目标与范围

目标是省掉连续短连接反复拨号的成本，同时保住 Linux splice 和裸数据通道。每条通道同一时间只承载一个业务。业务正常结束、双方确认后，通道立刻回池；连续空闲 60 秒才关闭。空闲超时可配置，空闲池和活动通道一起受每客户端资源上限约束。

只复用 sertun 客户端和服务端之间的业务通道。访问者和本地服务各自的 TCP 连接照常结束，不复用 SSH、HTTP 这类应用会话。不做并发多路复用，也不预先填固定数量的连接。

## 通道和业务的边界

控制连接继续管身份和会话，另外负责通道分配、方向结束和回收确认。每条通道有独立标识，每次分配生成新的业务标识；所有控制消息都绑定当前控制会话，过期消息直接拒绝。

业务通道只传载荷，不插入持续的数据帧头或结束标记，传输期间仍走原生 TCP 复制。业务源端读到正常 EOF 后，按复制函数成功写出的字节数，通过控制连接告诉对方这个方向的最终长度；不要对可复用通道发 FIN。

控制消息和载荷可能不走同一条连接，到达顺序没有保证。接收端必须按本方向的最终字节数交付完，才能把 EOF 交给真正的业务端；收到结束通知不等于数据已经到齐。最终计数对不上、方向提前物理 EOF、或者数据交付失败，销毁整条通道。

两个方向独立结束。一个方向完成后，对真正的业务目标执行 `CloseWrite()`，另一个方向继续传。只有双方都确认两个方向完成，旧的复制任务也全部退出，才允许复用。

## Linux splice 的收尾

持续传输走原生 TCP 的 `ReadFrom`。结束通知到达后，要协调接收方向停止等待物理 EOF：

1. 由这个方向的唯一所有者给源通道设读 deadline，把阻塞的读唤醒。
2. 等原复制任务退出，拿到成功交付的累计字节数，再清掉这次读 deadline。
3. 如果还有没交付的数据，以原生 TCP 为底层，用 `io.LimitedReader` 精确复制剩余字节，并校验完整交付。
4. 完成业务端的半关闭，再发本方向的交付确认。

Go 的 Linux 实现能识别 `io.LimitedReader`，据此限制 splice 的剩余长度，见[标准库源码](https://go.dev/src/net/splice_linux.go)。源读 deadline 不能立刻打断已经阻塞的目标写入；必须等内核 pipe 里已取走的数据写完，或者在收尾超时后销毁通道。真实的复制错误不能当成可恢复的协议唤醒继续传。

这套协调要在 Linux 上实测，至少覆盖部分进度、目标背压和 deadline 竞争；目前只有标准库路径作为依据。其他系统继续用用户态复制，遵守同样的业务边界。

## 分配和空闲回收

服务端统一管通道分配和空闲过期，不让两端各自抢。状态可以写成：

`新建 → 分配中 → 转发中 → 收尾中 → 空闲 → 分配中`，任何状态都能转到关闭。

- 新访问优先拿空闲通道，没有可用的再按需新建。
- 收尾确认之前，不开下一个业务，也不让新旧读任务重叠。
- 入池就开始 60 秒空闲计时；再次分配时取消旧计时，下次入池重新计。
- 过期回收和新分配必须在同一个状态转换里决出胜负。池满时关掉多余的空闲通道。
- 空闲时释放业务缓冲和复制任务，只留连接和必要状态。
- 控制会话失效时，关掉这个会话的全部活动和空闲通道。
- 第一版只复用正常收尾的通道。异常、计数不符、对端失效和收尾超时都销毁通道；数据发出去以后不自动重放请求。

## 兼容性和验收

新增控制消息会改变协议能力。动手前先定版本协商和不兼容时的拒绝行为，不能把旧实现的物理 EOF 当成可复用的结束。

按最小充分原则验证，至少覆盖：

- 同一条通道连续承载两个内容不同的业务，覆盖一个方向先结束、反向尾部数据、控制消息先于载荷到达，确认不串流、不截断。
- 覆盖收尾时的目标背压、取消或失败，以及过期回收和新分配竞争，确认连接、任务和资源上限都能收回来。
- 在 Linux 上实际核对持续传输和限长收尾仍然经过 splice；macOS / Windows 验证同样的关闭语义。
- 用相同工具链和链路对照短连接延迟、长流 CPU / 吞吐和空闲池资源增长。60 秒只是初始值，不代表已经验证过是最佳参数。

实现顺序：先做业务边界和收尾，再接空闲池，最后看资源和性能。不要把这个设计当成 HY2 多连接退化问题的既定修复。
